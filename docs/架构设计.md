# AI 集群平台 · 架构设计

> 目标：把多个 AI Agent 组织成一个可调度、可观测、可计费、可扩展的「集群」，
> 对外表现为一个能完成复杂任务的 AI 团队，而不是一堆孤立的聊天窗口。

---

## 1. 先定义清楚「集群」是什么

多 Agent 集群不是「同时开几个 GPT 窗口」。它至少要有四个能力：

| 能力 | 说明 | 没有它会怎样 |
| --- | --- | --- |
| 任务分解 | 把一个目标拆成有依赖关系的 DAG | 所有 Agent 重复做同一件事 |
| 能力路由 | 按 Agent 的专长/工具/模型分派任务 | 所有任务挤给同一个通用 Agent |
| 共享状态 | 任务结果、产物、上下文可被下游读取 | Agent 之间靠复述传话，信息衰减 |
| 生命周期管理 | 重试、超时、取消、预算、审计 | 一旦某个 Agent 跑飞，整场失控 |

所以平台的核心不是「调用模型」，而是**调度 + 状态机 + 消息总线**。模型只是 Worker 里的一个执行器。

## 2. 总体架构

```
                    ┌─────────────────────────────────────────┐
                    │              Web 控制台 / CLI            │
                    │   任务看板 · 实时日志 · 成本 · 回放       │

                                        │ REST + SSE/WebSocket
                    ┌───────────────────▼─────────────────────┐

                    └───────┬───────────────────────┬─────────┘
                            │                       │

                            │ 派发 Task             │ 事件

    │ 规划 Agent │     │ 检索 Agent │           │ 编码 Agent │  │ 追踪/计费  │
    └─────┬─────┘     └─────┬─────┘           └─────┬─────┘  └───────────┘

                    ┌───────────────────▼─────────────────────┐
                    │  State Store                            │

                    │  pgvector（记忆/检索） · S3（产物）       │
```

### 2.1 组件职责

- **Control Plane**：唯一对外入口。创建 Run、查询状态、取消、订阅事件、配额校验。无状态，可水平扩容。
- **Orchestrator**：集群的大脑。只做三件事：规划 DAG、按能力调度、推进状态机。**不执行具体任务**，因此可以独立重启和扩容（用 Redis 锁或 PG advisory lock 选主）。
- **Worker**：真正跑 Agent Loop 的进程。无状态，从总线拉任务，执行完写回结果。可以按能力分组部署（如 `gpu` 组、`web` 组）。
- **Event Bus**：所有状态变化的唯一事实来源。UI、计费、审计、告警都只订阅事件，不直接读业务库。
- **State Store**：Run/Task 的权威状态 + 事件日志 + 产物。事件日志天然支持「回放」。
- **Tool Gateway**：统一收口工具调用。这一层负责权限、超时、沙箱、审计，是安全边界。
- **Observer**：消费事件做指标、成本归集、异常检测，不阻塞主链路。

## 3. 领域模型（先定协议，再写代码）

```text
Run（一次集群运行）
 ├── goal            用户目标
 ├── status          planning | running | succeeded | failed | cancelled
 ├── budget          max_steps / max_tokens / max_usd / deadline
 ├── tasks[]         Task DAG
 └── artifacts[]     产物引用

Task（最小调度单元）
 ├── id
 ├── instruction     给 Agent 的自然语言指令
 ├── capability      需要的能能力标签（planner / research / code / review）
 ├── depends_on[]    前置 Task
 ├── status          pending | ready | running | done | failed | skipped
 ├── assignee        实际执行的 Agent
 ├── result          结构化结果
 └── attempts / error

Agent（可注册的 Worker 配置）
 ├── id / name
 ├── capabilities[]  能力标签
 ├── model           模型标识（可含 fallback）
 ├── system_prompt
 ├── tools[]         允许使用的工具白名单
 └── limits          max_steps / timeout / concurrency
```

**关键设计：Task 与 Agent 解耦。** 规划器只产出「需要什么能力」，调度器再决定「谁来干」。这样换模型、加机器、灰度新 Agent 都不需要改规划逻辑。

### 3.1 事件协议

所有事件统一信封，便于回放和跨语言消费：

```json
{
  "id": "evt_...",
  "run_id": "run_...",
  "task_id": "task_...",
  "type": "task.completed",
  "ts": 1730000000.123,
  "seq": 42,
  "payload": { "result": "...", "tokens": 1234, "cost_usd": 0.002 }
}
```

事件类型最小集合：

`run.created` `run.planned` `run.completed` `run.failed` `run.cancelled`
`task.ready` `task.started` `task.completed` `task.failed` `task.retried`
`agent.step` `tool.called` `tool.result` `budget.exceeded`

**约定：状态只能由事件驱动变更。** 不要在 API 里直接改 task.status，否则回放会对不上。

## 4. 核心流程

### 4.1 提交与规划

1. `POST /api/runs` 写入 Run（status=planning），返回 `run_id`。
2. Orchestrator 调 Planner（LLM + 结构化输出）生成 Task 列表。
3. 校验 DAG：无环、依赖存在、至少一个入口；不合法则让 Planner 重试一次，仍失败则 `run.failed`。
4. 落库并发布 `run.planned`。

> 规划器输出必须是 **JSON Schema 约束的结构化结果**，不要解析自然语言。
> 这是多 Agent 系统里最容易翻车的地方。

### 4.2 调度

调度循环（每 200ms ~ 1s 一轮，或由事件触发）：

```
ready = tasks where status=pending and all(dep.status=done)
for task in ready:
    agent = pick_agent(task.capability)   # 能力匹配 + 最少负载 + 健康检查
    if agent and global_concurrency_ok:
        task.status = running
        publish(task.ready) → 投递到 agent 的队列
```

调度策略按阶段演进：

| 阶段 | 策略 |
| --- | --- |
| MVP | 能力标签精确匹配 + 最少运行任务数 |
| 成长期 | 加权（成功率、延迟、成本）+ 模型 fallback |
| 成熟期 | 优先级队列、抢占、亲和性（数据 locality）、多租户配额 |

### 4.3 Worker 执行（Agent Loop）

```
messages = [system_prompt, task.instruction, 上游 Task 的结果摘要]
for step in range(max_steps):
    resp = llm(messages, tools=allowed_tools)
    if resp.tool_calls:
        for call in resp.tool_calls:
            result = tool_gateway.invoke(call)   # 权限/超时/沙箱/审计
            messages.append(tool_result)
    else:
        return resp.content
raise StepLimitExceeded
```

要点：

- **上游结果只传摘要 + 产物引用**，不要把所有上下文拼进去，否则 token 会指数爆炸。
- 每一步都发 `agent.step` 事件，UI 才能流式展示「它正在想什么」。
- Worker 必须支持**幂等**：同一个 task 重投时不能产生重复副作用（用 `task_id + attempt` 做幂等键）。

### 4.4 汇聚

所有 Task 完成后，由 Orchestrator 做最终汇总（可选择性地再调一次「总结 Agent」），写入 Run.result，发布 `run.completed`。

## 5. 技术选型

### 5.1 推荐组合

| 层 | MVP | 生产 |
| --- | --- | --- |
| 语言 | Python 3.12+ | 同左；高并发网关可用 Go/Node |
| Web 框架 | FastAPI | FastAPI + Gunicorn/Uvicorn |
| 编排 | 自研状态机（本仓库） | 自研 或 LangGraph/Temporal |
| 消息 | 进程内 asyncio 队列 | Redis Streams → NATS JetStream / Kafka |
| 数据库 | SQLite | PostgreSQL 16 |
| 向量 | 无 / 内存 | pgvector / Qdrant |
| 产物 | 本地目录 | S3 / MinIO |
| 沙箱 | 子进程 + 超时 | Docker + gVisor / Firecracker；前端工具用 WASM |
| 前端 | 单页 HTML + SSE | Next.js + shadcn/ui + WebSocket |
| 观测 | 结构化日志 | OpenTelemetry + Prometheus + Grafana + Langfuse |
| 部署 | `uvicorn` | Docker Compose → Kubernetes + Helm |

### 5.2 为什么编排自研而不是直接上框架

LangGraph / CrewAI / AutoGen 适合快速验证，但生产环境通常需要：

- 精确控制重试、超时、幂等、预算；
- 与自有权限、计费、审计系统集成；
- 任务状态持久化与断点恢复；
- 多租户隔离。

建议：**MVP 用自研的 200 行状态机**（本仓库即如此），把框架当参考实现。等业务模型稳定后再决定是否引入 Temporal 这类工作流引擎。

### 5.3 插件/工具协议

统一走 **MCP（Model Context Protocol）**：

- 工具以 MCP Server 形式提供，平台只做 MCP Client + 网关；
- 新增工具不需要改平台代码；
- 天然支持 stdio / HTTP 两种传输。

插件清单示例：

```json
{
  "name": "web-search",
  "version": "1.0.0",
  "transport": "http",
  "endpoint": "http://127.0.0.1:7801/mcp",
  "permissions": ["network:outbound"],
  "tools": ["search", "fetch_page"]
}
```

Agent 只能调用其 manifest 中 `tools[]` 白名单内的工具。

## 6. 可靠性与安全（生产必须做）

### 6.1 失败处理

- **至少一次投递 + 幂等消费**：不要追求 exactly-once。
- **重试策略**：指数退避 + 抖动，区分可重试（超时/429/5xx）与不可重试（400/权限）。
- **超时**：Task 级 + Step 级双层超时，防止单次 LLM 调用挂死。
- **死锁检测**：若存在 pending 任务但无可运行任务且无 running 任务 → 判定 DAG 卡死，`run.failed`。
- **取消**：`DELETE /api/runs/{id}` 置取消标记，Worker 在每个 step 边界检查。

### 6.2 预算与成本

- Run 级预算：`max_tokens`、`max_usd`、`deadline`、`max_steps`。
- 每次 LLM 响应后累加，超限立即 `budget.exceeded` 并取消剩余任务。
- 成本按 `Agent × 模型 × 租户` 归集，便于内部结算。
- **提示词缓存**和**结果缓存**（相同 instruction 哈希）能省 30%+。

### 6.3 安全边界

- Agent 生成的代码**绝不在主进程执行**，进沙箱，默认无网络。
- 工具网关做参数校验（JSON Schema）+ 出站域名白名单 + 审计日志。
- 密钥不进入 prompt：工具层注入，模型只看到占位符。
- 多租户：Run/Task/Artifact 全部带 `tenant_id`，数据库行级安全。
- Prompt 注入防护：外部内容标记为不可信，工具结果与系统指令分区存放。

### 6.4 可观测性

三个必看面板：

1. **运行视图**：Run 的 DAG、每个节点的状态/耗时/重试次数。
2. **成本视图**：按模型/Agent/租户的 token 与金额。
3. **质量视图**：任务成功率、平均步数、工具错误率、人工介入率。

Trace 建议用 OpenTelemetry：`run` 是 root span，`task` 是 child span，`llm.call` / `tool.call` 是 leaf span。这样能直接看出时间花在哪。

## 7. 路线图

### Phase 0 · 验证（1 周）
- 明确 1 个真实场景（如「竞品调研报告」或「代码库升级」）。
- 手工跑通「拆解 → 并行 → 汇总」，确认价值。
- 产出：场景 SOP + 成功标准（准确率/耗时/成本）。

### Phase 1 · MVP（3–4 周）
- 单机、进程内总线、SQLite。
- Planner + 3~5 个 Agent + 5 个工具。
- SSE 实时看板。
- 预算与取消。
- 目标：端到端跑通 20 个真实任务，成功率 > 70%。

### Phase 2 · 可运营（6–8 周）
- Postgres + Redis Streams，Worker 独立部署、可水平扩容。
- 多租户、鉴权、配额。
- MCP 工具市场、Agent 注册中心。
- 重试/幂等/死锁恢复、回放。
- OpenTelemetry + 成本看板。
- 目标：可对外小范围试用。

### Phase 3 · 平台化（3–6 个月）
- K8s 部署、弹性伸缩、GPU 节点池。
- 可视化编排（DAG 编辑器）+ 版本化。
- 评测集与自动回归（每次改 prompt/模型都跑）。
- 插件审核、签名、沙箱隔离。
- 目标：多团队自助接入。

## 8. 最容易踩的坑

1. **上下文爆炸**：把上游全文塞给下游。解决：摘要 + 产物引用 + 按需检索。
2. **规划器胡说**：输出无法执行的 DAG。解决：JSON Schema + 校验 + 重试 + 降级为固定模板。
3. **无限循环**：两个 Agent 互相「再确认一下」。解决：硬性 `max_steps` + 全局 deadline + 重复指令检测。
4. **成本失控**：并行度太高。解决：全局并发上限 + 预算熔断。
5. **状态不一致**：API 直接改库。解决：事件溯源，所有变更走同一条路径。
6. **过早引入框架**：被框架的抽象绑死。解决：先写最小状态机，按需替换。
7. **没有评测**：改一个 prompt 不知道变好还是变坏。解决：从第一天就积累任务集和人工评分。

## 9. 本仓库的 MVP 实现

`mvp/` 是一个零外部依赖即可启动的最小实现，用来看清上面每个概念如何落地：

- 进程内事件总线（可替换为 Redis Streams）
- SQLite 持久化 Run / Task / Event
- 能力路由调度器 + DAG 依赖
- 可插拔 LLM（默认 mock，可切 OpenAI 兼容接口）
- 工具注册表（含沙箱化的 `calc`）
- SSE 实时事件流 + 单页看板
- 预算、步数上限、死锁检测、取消

启动方式见根目录 `README.md`。

它刻意**没有**做：鉴权、多租户、分布式 Worker、MCP 接入、向量记忆。这些是 Phase 2 的工作，接口已预留。
