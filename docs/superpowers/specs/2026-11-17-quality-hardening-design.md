# 质量硬化设计（2026-11-17）

> 状态：M0–M1 已实施（2026-11-17，147 项测试通过）；M2–M4 待做
> 基线：`c4cbd1a`（当前提交 `518af0e`）
> 输入：`HANDOVER.md`、`docs/2026-11-17-审计报告.md`

## 1. 意图与为什么现在做

交接文档把项目定义为“单人使用的多 Agent 集群”，验收口径是一句话：

> 手机打开一个地址，选一台在线电脑和目录，发任务；需要审批时手机能收到提醒；电脑断线、服务器重启都不丢任务；记录能看出是哪台机器、哪个目录跑的。

2026-11-17 的审计发现，这条验收线目前有四处**结构性**缺口：

1. 鉴权在一种很常见的误配下可以被空口令绕过（SEC-01，P0）。
2. 专家团模式下“停止运行”取消不掉，且会和主调度器打架（RUN-01/RUN-02）。
3. 断点恢复可能恢复出一个必然 400 的任务（RUN-03）。
4. 桌面端空闲时看不到手机发起的新运行，也收不到审批（UI-05）。

这些不是“再加一个功能”能解决的，继续按原路线图做 P1 可见性，会在调试这些缺陷时反复返工。所以本期先把这条验收线补牢，再回到功能路线。

## 2. 目标

- **G1 鉴权不可绕过**：空值、空白值、非 ASCII、`.env` 异常形态都不放行；文档端点默认关闭。
- **G2 停止即停止**：取消能真正终止专家团轮次，不把终态改写成 failed，取消后不再花钱。
- **G3 恢复必可恢复**：checkpoint 只在消息序列合法时落库，恢复后不会因 tool-call 未配对而 400。
- **G4 不重复计费**：重复 Enter、重复点重跑、运行中重跑，都只产生一个运行。
- **G5 手机闭环可见**：桌面端空闲时也能看到新运行与审批；快速切换运行不会串台。
- **G6 有测试网**：建立 pytest 地基，让后续修 bug 和改调度有自动化验证，不再只靠手工清单。

## 3. 非目标

- 不做多用户 / RBAC / 团队协作。
- 不做多副本高可用（仍是单进程 asyncio）。
- 不把 worker 做成强安全沙箱。
- 不引入 Alembic、前端构建链、TypeScript、框架级重构。
- 不在本期实现 HANDOVER P3 的设备级队列和远程 cancel（它们是功能，不是缺陷修复），但会把接口预留出来。

## 4. 反目标（即使“技术上完成了”也算失败）

- 修了缺陷但没有对应测试，下次改动又回归。
- 用 `try/except` 把 500 吞成静默失败，用户看不到错误。
- 为了赶进度新增一条绕过认证中间件的 `/api` 路由。
- 自动 `git commit` / `git push`（HANDOVER §1.3 明确禁止）。
- 把 `mvp/.env`、`mvp/data/cluster.db` 提交进仓库，或把它们作为测试库。

## 5. 约束

- Python 3.14.1，Node v24.19.0；后端 `fastapi`/`uvicorn[standard]`/`httpx`/`pydantic`/`websockets`。
- 单进程 asyncio；`DeviceHub`、审批 future、EventBus 订阅都在内存。
- SQLite 无迁移框架；新增列必须幂等。
- 前端单文件 `mvp/static/index.html`，无构建、无前端测试，改动后必须 `node --check`。
- 后端改动必须重启服务验证；前端改动必须跑 `node --check`。
- 测试必须显式设置 `ACCESS_TOKEN` 与临时 `DATA_DIR`，否则 `config` 首次导入会写真实 `mvp/.env`（HANDOVER §16.13）。
- 交付前停掉服务器和 worker，不留后台进程。

## 6. 方案选择

### 方案 A：按 HANDOVER 路线图继续做功能（P1 → P5）

- 做法：先做“运行详情/历史无条件显示设备与目录”，再手机通知、PWA、设备并发。
- 优点：用户可见价值最快。
- 缺点：P0 鉴权绕过仍在；专家团取消/恢复缺陷会在每次功能验收时干扰；没有测试网，改前端状态机和调度器风险高。
- 结论：不单独采用。P1 可见性可以并到本期最后一个里程碑，但不作为第一件事。

### 方案 B：测试地基 + P0/P1 硬化，再回到功能路线（推荐）

- 做法：M0 测试地基 → M1 安全与数据正确性 → M2 运行/调度正确性 → M3 前端状态与手机闭环 → M4 交接 P1 可见性。
- 优点：先补“任务不丢、停止有效、不重复计费、手机能看到”；pytest 让后续每一步都有回归保护；不改变架构。
- 缺点：短期可见功能少，粗略估计 2–3 个工作日（不含 M4 功能）。
- 风险：`main.py`/`orchestrator.py` 较大，测试需要先用 monkeypatch 隔离 LLM 与设备；M0 必须先做。

### 方案 C：大重构（拆分模块、Alembic、前端构建、多进程）

- 做法：把 `main.py` 拆成 routers、`orchestrator.py` 拆成 planner/scheduler/executor，引入迁移框架和前端构建。
- 优点：长期结构好，多副本更容易。
- 缺点：单人项目，收益/风险比低；会推迟所有功能；当前缺陷不需要重构也能修。
- 结论：不做。只在方案 B 内做必要的小抽出（如 `_child_env()`、`_json_or()`、`_token_ok()`），不搞大搬迁。

**推荐方案 B。** 本设计文档和随附计划都按 B 写。

## 7. 分期与验收

### M0 测试地基（预计 0.5 天）

- `mvp/tests/conftest.py` 在导入 `mvp.app` 前设置 `ACCESS_TOKEN=test-token`、临时 `DATA_DIR`、`ENABLE_SHELL=0`、mock 模型。
- `TestClient` 夹具、登录夹具、临时 workspace 夹具。
- 一条 smoke：`/api/health` 公开 200，`/api/meta` 未登录 401。
- 验收：`pytest -q` 全绿；跑完后真实 `mvp/data/cluster.db` 行数不变，`mvp/.env` 未被改写。

### M1 安全与数据正确性（预计 1 天）

- SEC-01/02/03 一次改完；SEC-04 关闭文档端点；SEC-07 子进程环境白名单；SEC-08 SSRF 与响应上限。
- DATA-01 删除运行级联 messages；DATA-02 JSON 容错；DATA-03 SSE 回放分页 + `Last-Event-ID`。
- DATA-04/05 设备删除关闭 WS、worker 非法帧容错。
- 验收：审计报告中这些条目的复现测试全部转绿；`pytest -q` 全绿；`compileall` 通过。

### M2 运行与调度正确性（预计 1 天）

- RUN-01 单一调度锁 + planning 拒绝新轮；RUN-02 轮次可取消；RUN-03 checkpoint 深拷贝与完整批次；RUN-04/05 终态保护；RUN-07 token 估算。
- 验收：并发/取消/恢复的确定性测试通过；手工跑一次 mock 专家团，停止后 DB 状态为 `cancelled`，无 `failed` 覆盖。

### M3 前端状态与手机闭环（预计 1 天）

- UI-01 提交去重；UI-02 运行切换守卫与事件作用域；UI-03 对话流作用域；UI-04 重跑保护；UI-05 后台刷新去门控。
- 验收：`node --check` 通过；手工清单：双 Enter 只建一个运行、快速切换不串台、桌面空闲时能看到手机发起的新运行与审批。

### M4 交接 P1 可见性（预计 1 天）

- HANDOVER §17 P1：运行详情无条件显示设备与目录、历史列表设备标记、工具事件带目标路径。
- 验收：点开任意历史，能回答“哪台机器、哪个目录、改了什么”。

### 后续（不在本期计划内）

- 其余 P2：DEV-01…10、SEC-10…15、OPS-01…06、UI-06…17。
- HANDOVER P2/P3/P4/P5：Web Notification、PWA、设备并发队列、远程 cancel、云端实跑、备份脚本。

## 8. 已决定的技术选择

| 决策 | 选择 | 理由 |
|---|---|---|
| 测试框架 | pytest（新增 `mvp/requirements-dev.txt`） | 项目已有 FastAPI，`TestClient` 可直接用；不引入额外运行时依赖 |
| 测试隔离 | 临时 `DATA_DIR` + 显式 `ACCESS_TOKEN` + mock 模型 | 避免写真实库、避免触发首次 token 生成副作用 |
| 鉴权比较 | UTF-8 bytes + 先拒绝空值 | 同时修 SEC-01 与 SEC-03，不需要额外依赖 |
| 文档端点 | 默认关闭，`ENABLE_API_DOCS=1` 打开且走鉴权 | 默认安全，开发时仍可用 |
| 调度互斥 | 每个 run 一把 `asyncio.Lock`，所有调度入口共用 | 不改变单进程模型，最小改动解决双调度器 |
| checkpoint | `copy.deepcopy` + 完整工具批次边界保存 | 保持旧 checkpoint 向后兼容，不引入新表 |
| SSE 回放 | 分批续拉 + 读 `Last-Event-ID` | 与 EventSource 标准重连语义对齐 |
| 前端守卫 | `state.submitting` / `state.rerunning` / runId 作用域 | 单文件前端，不引入框架 |

## 9. 留给实现者的空间

- 测试文件的具体命名与 fixture 组织，只要满足“不污染真实库”即可。
- `_json_or`、`_child_env`、`_token_ok` 放在哪个模块，按就近原则。
- 设备心跳超时的默认值（建议 60 秒，与 `DEVICE_WAIT_SEC` 对齐）。
- M2 的并发测试用 monkeypatch 还是 fake LLM，按可读性选择。
- M4 的设备标记样式（缩写/图标/颜色），只要在窄屏不挤爆。

## 10. 风险与回滚

| 风险 | 缓解 |
|---|---|
| 测试导入 `mvp.app.main` 时触发真实库写入 | conftest 在 import 前设置 `DATA_DIR`；M0 验收专门检查真实库行数 |
| SEC-07 环境白名单过严导致命令缺 `PATH`/`HOME` | 用“剔除名单”而不是“只留白名单”；测试覆盖 `PATH` 仍存在 |
| RUN-01 加锁后死锁 | 锁只在 run 级，顺序固定；测试用超时断言；`_drive` 与 `_run_round` 不互相 await |
| RUN-03 深拷贝导致大 checkpoint 内存上升 | 只在保存点深拷贝，且 checkpoint 本身已有体积上限问题（P2 另议） |
| UI 改动破坏现有流式 | 每个 UI 任务都跑 `node --check`，并按手工清单回归一次 mock 运行 |
| 修 SEC-01 后用户已清空 token 无法登录 | 启动时重新生成并打印一次；在 README/启动日志中说明 |

## 11. 验收口径（本期整体）

1. `pytest -q` 全绿，且跑完后 `mvp/data/cluster.db` 与 `mvp/.env` 未被修改。
2. `python -m compileall -q mvp/app mvp/worker mvp/scripts` 通过。
3. `node --check` 通过（抽取 `index.html` 内联脚本）。
4. 手工：空 token 配置启动被拒绝或重新生成；`Authorization: Bearer ` 返回 401；`/openapi.json` 未登录 404/401。
5. 手工：mock 专家团运行中取消，DB 终态为 `cancelled`，无后续 LLM 调用。
6. 手工：桌面端空闲时手机发起运行，10 秒内桌面列表出现该运行；审批能弹出。
7. 手工：连按两次 Enter、运行中连点重跑，都只产生一个运行。
8. 点开任意历史，能看到设备名与工作区目录。
